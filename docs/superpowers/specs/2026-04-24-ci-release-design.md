# CI and Release Design

## Goal

Add a minimal, reliable GitHub Actions setup for `opah.fish` that:

- validates changes on pushes and pull requests
- publishes tagged releases to GitHub Releases
- reuses the existing local developer commands in `justfile`
- requires no 1Password configuration or secrets in CI

## Current State

- The repository has no `.github/workflows` directory yet.
- The project already has two core verification commands:
  - `just lint`
  - `just test`
- The test suite now uses mocked `op` behavior, so CI does not need a real 1Password vault or CLI authentication.
- Releases today are implicit git state only; there is no defined automated release pipeline.

## Scope

This design covers:

- pull request and push validation in GitHub Actions
- tagged release creation in GitHub Actions
- release artifact generation from repository contents
- the expected operator flow for cutting a release

This design does not cover:

- changelog generation beyond GitHub autogenerated notes
- package publishing to an external registry
- Homebrew taps, custom installers, or marketplace publishing
- signing, notarization, or secret-backed deployment steps
- branch protection configuration in GitHub settings

## Design Overview

The system will use two workflows:

1. `ci.yml`
2. `release.yml`

The CI workflow is the default quality gate for active development. The release workflow is tag-driven and reruns the same project checks before publishing a GitHub Release.

The workflows intentionally stay simple:

- single operating system: `ubuntu-latest`
- single verification entrypoint: the existing `just` recipes
- tag-based releases using semantic version tags like `v0.1.0`

This keeps the automation aligned with the repo’s current size and maintenance needs while leaving room to add matrices or richer release logic later.

## Approach Options Considered

### Option 1: Merge-Based Releases

Create releases automatically whenever code lands on `main`.

Pros:

- lowest operator effort
- every merge is immediately releasable

Cons:

- too aggressive for a plugin repo with manual version intent
- weak audit trail for version boundaries
- harder to separate “merged” from “published”

### Option 2: Manual Dispatch Releases

Create releases only through `workflow_dispatch`.

Pros:

- explicit operator control
- no tag management required

Cons:

- easy to drift from semver tags used by plugin consumers
- more manual workflow state to remember
- weaker correspondence between git history and releases

### Option 3: Tag-Driven Releases

Create releases from semantic version tags and publish a matching GitHub Release.

Pros:

- clean version boundaries
- natural fit for Fisher and Oh My Fish consumers who already install from git
- easy to reason about and roll back
- keeps tags as the canonical version identifier

Cons:

- requires an explicit tagging step

### Recommendation

Use Option 3.

It is the best fit for an open-source Fish plugin because it preserves simple git-based distribution while adding a proper release record and repeatable automation.

## CI Workflow Design

### File

`.github/workflows/ci.yml`

### Triggers

- `pull_request`
- `push`

Pushes should run for `main` and other active branches. Pull requests should run regardless of source branch.

### Concurrency

Enable workflow concurrency by workflow name and ref so new pushes cancel stale runs for the same branch or PR.

### Environment Setup

The workflow installs:

- Fish shell
- `just`
- `fishtape`

The workflow should not assume these tools already exist on the GitHub runner image.

### Steps

1. Check out the repository.
2. Install Fish shell.
3. Install `just`.
4. Install `fishtape` in a reproducible way.
5. Run `just lint`.
6. Run `just test`.

### Behavior

- Any lint or test failure fails the workflow.
- No secrets are configured or required.
- CI output should make it obvious whether the failure came from syntax validation or tests.

## Release Workflow Design

### File

`.github/workflows/release.yml`

### Trigger

- `push` on tags matching `v*`

Examples:

- `v0.1.0`
- `v1.2.3`

Non-version tags are out of scope.

### Release Flow

1. Check out the repository at the tag.
2. Install Fish shell, `just`, and `fishtape`.
3. Run `just ci`.
4. Create release archives.
5. Create a GitHub Release for the pushed tag.
6. Attach the archives to that release.

### Artifact Shape

Release artifacts should be source-style archives containing the plugin contents required for installation.

Initial release artifacts:

- `.tar.gz`
- `.zip`

The archive prefix should include the project name and version, for example:

- `opah.fish-v0.1.0.tar.gz`
- `opah.fish-v0.1.0.zip`

Artifacts should contain the repository files needed for plugin installation and exclude git metadata.

### Release Notes

Use GitHub autogenerated release notes initially.

This keeps the workflow lightweight while still giving users a readable changelog summary. If the project later needs curated notes or changelog files, that can be added as a separate improvement.

### Failure Semantics

- If `just ci` fails, the release workflow must fail and no release should be published.
- If archive creation fails, the workflow must fail before publishing.
- If Release creation fails after artifacts exist, the workflow should fail visibly so the operator can retry from the tag.

## Operator Workflow

The expected human release flow is:

1. Merge release-ready changes to `main`.
2. Create and push a semantic version tag, such as `v0.1.0`.
3. Let GitHub Actions run the release workflow.
4. Review the published GitHub Release and attached archives.

This keeps release intent explicit and avoids accidental publishing from ordinary merges.

## Testing Strategy For Automation

The workflows rely on the existing repo commands instead of duplicating command logic in YAML.

That means:

- local verification and CI verification stay aligned
- future test or lint changes should usually happen in `justfile`
- workflow YAML remains thin orchestration rather than policy

Because the test suite is fully mocked for `op` interactions, the automation can run in GitHub-hosted runners without any 1Password account, vault access, or secrets.

## Security and Secrets Posture

- CI and release workflows should use the default repository `GITHUB_TOKEN` only.
- No 1Password secrets, API tokens, or environment configuration are required.
- Release publishing should rely on GitHub’s standard permissions needed to create releases and upload assets.

## Future Extensions

Possible follow-up improvements after the initial rollout:

- add a macOS CI job alongside Ubuntu
- add README installation smoke checks
- add a version validation step to ensure tag format is semver
- add a changelog file or curated release notes process
- add a workflow_dispatch path for re-running release publication manually

## Implementation Notes

Implementation should favor small, explicit workflows and avoid over-abstracting reusable actions until the project actually needs them.

The expected first implementation is:

- one CI workflow file
- one release workflow file
- any supporting `justfile` refinements required for reproducible CI setup
- README updates describing the release process only if the final workflows materially change contributor expectations

## Acceptance Criteria

The design is considered implemented when:

1. Pull requests run GitHub Actions that execute `just lint` and `just test`.
2. Pushes to active branches run the same validation workflow.
3. Pushing a tag like `v0.1.0` triggers a release workflow.
4. The release workflow reruns project verification before publishing.
5. The release workflow publishes a GitHub Release with attached `.tar.gz` and `.zip` artifacts.
6. No CI or release job requires access to a real 1Password vault.
